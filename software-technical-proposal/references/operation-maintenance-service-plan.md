# operation-maintenance-service-plan

## 适用场景

1. 平台运维、网站运维、系统运维、机房网络综合运维、驻场服务、年度服务项目。
2. 采购文件重点要求 SLA、巡检监控、事件管理、问题管理、变更管理、备份恢复、安全加固、值守排班、报告机制和交接。
3. 用户要求“像运维负责人写的履约方案”，而不是系统建设技术方案。

## 模板定位

1. 文档外观：规则性强、黑灰正式、少装饰，允许较多表格。
2. 正文风格：服务对象、服务级别、流程闭环、台账记录和报告机制优先。
3. 结构策略：围绕“对象范围、服务台、巡检、事件、变更、备份、安全、报告、交接、优化”组织。
4. 交付形态：DOCX 为主；服务闭环图、值守升级图、备份恢复链路和监控告警闭环作为支撑图示。

## 内容写法

1. 运维不等于售后电话。必须写服务受理、分级、处理、复核、关闭、复盘和知识沉淀。
2. SLA、巡检频次、值守时间、恢复时限、人员数量等数字型承诺必须来自采购文件或用户确认事实。
3. 服务边界要写清：哪些系统、设备、数据、网络、账号、接口和第三方服务在范围内，哪些需要业主或第三方配合。
4. 事件管理写闭环，问题管理写根因和复盘，变更管理写申请、评估、审批、实施、验证和回退。
5. 报告机制要写报告周期、内容、提交对象和整改跟踪，不写“定期汇报”这种废话。
6. 固定表单按采购文件保留；叙述性正文不写“评分响应、评委、为了得分”。

## 图示建议

1. 服务闭环图：受理、分派、处理、复测、确认、关闭、复盘。
2. 值守升级图：一线值守、二线技术、专项支持、管理升级。
3. 备份恢复链路图：备份对象、备份介质、校验、恢复演练、恢复确认。
4. 监控告警闭环图：采集、告警、确认、处置、回写、统计。

## 交付前检查

1. 运维对象、服务边界、服务时间和协同责任是否清楚。
2. SLA、巡检、应急、报告、交接五项是否闭环。
3. 事件、问题、变更是否分别写清，不混成一个“问题处理流程”。
4. 数字型承诺是否有来源。
5. 服务报告和台账是否有提交周期、内容和跟踪动作。
6. 支撑材料位置是否精确到章节号、图号、附表号、附件号或页码锚点。
7. 是否把运维方案误写成建设方案或售后电话清单。
8. 渲染页面是否无重叠、截断、表格贴边、异常空白。
