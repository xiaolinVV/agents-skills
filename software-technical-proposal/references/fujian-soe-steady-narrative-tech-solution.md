# fujian-soe-steady-narrative-tech-solution

## 适用场景

1. 福建省属国企、地方国企、国资监管单位、集团型企业、城投/交投/水投/能化/电子信息/大数据集团等采购或咨询类技术方案。
2. 用户要求“福建国企风格”“省属国企风格”“国企正式风格”“稳健一点”“像集团内部正式方案”“不要太互联网化”“叙述型正式技术方案”。
3. 项目涉及数字化转型、信创改造、数据治理、生产经营监管、安全运行、集团管控、AI+行业应用、智慧监管、平台建设、系统集成和运维服务。
4. 采购文件关注项目理解、总体建设思路、系统集成实施方案、进度控制、变更控制、质量保障、运行维护、技术支持、培训和验收。

## 模板定位

1. 文档外观：省属国企正式材料风格，稳重、清晰、少装饰，章节层级比默认模板更强。
2. 正文风格：站在业主和集团管理视角写方案，强调稳妥可控、责任闭环、过程留痕、风险前置和长期运营。
3. 结构策略：先讲项目定位和管理目标，再讲建设路径、技术架构、实施组织、质量进度变更控制、运维运营保障。
4. 交付形态：DOCX 为主，图示 HTML/SVG 和截图为支撑产物。
5. 供应商风格定位：本模板应像“稳健型系统集成与长期运营供应商”编写的方案，而不是通用软件开发商方案。叙述重点放在治理对象识别、运行机制固化、组织责任交接、质量门禁和持续服务台账。
6. 差异化铁律：如果同一采购文件已经存在 `formal-procurement-tech-solution` 产物，本模板必须从目录、图示、版式、语言和内容组织上明显避让。不得复用 formal 产物的章节序列、图名、图示构图、表格标题和段落开头。
7. 版式基调：默认黑灰正式、稳重叙述。标题、正文和表头文字使用黑灰色；不用蓝色字体、蓝色表头或互联网化彩色组件。

与 `formal-procurement-tech-solution` 的区别：

1. `formal-procurement-tech-solution` 更像项目技术负责人写的通用政企软件方案，重在业务闭环和技术能力说明。
2. `fujian-soe-steady-narrative-tech-solution` 更像省属国企或集团单位使用的正式技术方案，重在集团管控、合规安全、实施组织、运行维护和持续改进。
3. formal 可以按“项目理解、需求响应、系统总体、布局、创新、服务保障”展开；本模板应改用“治理对象、运行机制、平台承载、数据证据、交付管控、服务台账”的框架。
4. formal 常用系统分层图、业务闭环流程图、服务保障体系图；本模板应优先使用治理责任图、证据链路图、质量门禁图、交付作战图、运维台账闭环图等不同图示。
5. formal 可以更直接写技术模块；本模板应以“管理动作+系统承载+留痕资料+责任边界”写法组织，同一事实不能用同一段话换标题复用。
6. 本模板更强调叙述和机制说明，表格只辅助表达计划、职责、风险、交付物和服务响应，不把普通说明表格化。
7. 两者共享采购文件读取、正文克制表达、DOCX 质检和输出目录规则，但不共享目录骨架、图示集合、句式库和页面视觉。

## 内容写法

### 表格使用边界

1. 本模板是稳健叙述型技术方案。项目定位、建设路径、运行机制、质量进度变更控制和运维支持优先写成短段落和编号列表。
2. 表格只用于计划、职责、风险、交付物、服务响应、验收资料等需要逐项落责的内容。
3. 表格前后必须有说明文字，不能用连续表格替代方案论证。

### 交付正文边界

1. 正文只呈现省属国企正式材料风格的技术方案，不写写作过程、思考过程、模板差异化理由或 agent 对话痕迹。
2. 用户对语气、表格、措辞、风格提出的注意事项，只作为内部约束吸收。正文直接呈现稳重、克制、可交付的方案，不解释“不要互联网化”“不要营销化”。
3. 涉及范围、参数、工期、验收、承诺、责任边界的不确定事项，先向用户确认；确认前不写入 DOCX。
4. 正文不得出现“本文将、以下从几个方面、根据用户要求、按照您的要求、模板建议、AI 生成、评分响应、评委、待确认、需明确、暂按、后续确认”等过程性、答题卡式或未定稿表述。

1. 项目理解与建设定位
   1. 开头不要直接堆功能模块。先写本项目在业主单位管理体系中的位置：解决什么管理问题，支撑什么业务闭环，降低什么运行风险。
   2. 福建国企风格可以适度写“集团管控、生产经营、安全运行、合规管理、数字化转型、信创适配、数据治理”等关键词，但必须落到项目动作。
   3. 不要写空泛政治口号。采购文件没有要求党建、宣传、品牌展示时，不主动扩写。
   4. 对消防、交通、水利、能源、园区、国资监管等项目，要写清现有系统、现场单位、集团部门和一线人员之间的职责边界。

2. 总体建设思路
   1. 用“统一规划、分步实施、先稳后优、持续迭代”这类稳健路径组织，不写互联网式冲锋口号。
   2. 建设原则要能指导后文：现有系统不破坏、关键数据可追溯、安全合规可检查、业务流程可落地、运维责任可交接。
   3. 分阶段实施要对应采购工期，不要凭空编长期路线图。

3. 业务协同与管理闭环设计
   1. 把业务流程写成责任链，而不是功能清单。
   2. 每个流程都回答：谁发起、谁处理、谁审核、谁整改、谁归档、谁统计。
   3. 对监管、巡检、整改、维保、验收类项目，必须写问题台账、整改跟踪、复核确认和归档查询。
   4. 对集团型项目，写清集团、权属单位、现场单位、承建方、运维方之间的协同机制。

4. 系统总体技术方案
   1. 技术架构要服务管理目标，不要为了堆技术名词。
   2. 数据架构要写清数据来源、数据归集、数据质量、数据权限、数据留痕和数据共享边界。
   3. AI 项目必须写清人工确认边界。AI 是辅助分析和风险提示，不替代业务人员、管理人员或执法人员的最终判断。
   4. 信创相关内容只在采购文件要求或项目确有需要时写。写了就必须说明适配对象、迁移边界、测试验证和回退安排。
   5. 安全合规要写成控制动作：账号权限、日志审计、数据备份、漏洞修复、接口鉴权、传输加密、终端管理和运维审计。

5. 系统集成与实施方案
   1. 强调组织化交付，而不是“我们有经验”。
   2. 写清需求确认、方案深化、开发配置、联调测试、试运行、上线切换、验收移交的顺序。
   3. 每个阶段都要有产出物，例如需求确认单、实施计划、联调记录、问题台账、培训签到、验收资料。
   4. 不允许承诺无法控制的事项。涉及第三方接口、业主数据、现场网络、硬件到货时，要写前置条件和协同责任。

6. 质量、进度和变更控制
   1. 这是本模板的重点，不要写成泛泛的“加强管理”。
   2. 质量控制覆盖需求基线、设计评审、代码或配置复核、数据校验、接口联调、安全测试、试运行问题处理、验收资料复核。
   3. 进度控制写节点、责任人、检查频率、延期预警和纠偏措施。
   4. 变更控制写申请、影响评估、确认、实施、验证和归档，不允许口头变更直接进入开发。
   5. 风险控制写真实风险：接口资料不完整、历史数据质量差、现场网络波动、信创适配差异、AI 误报漏报、用户使用不充分、验收资料滞后。

7. 运行维护与技术支持
   1. 运维不只写售后电话。要写服务台账、响应等级、远程支持、现场支持、定期巡检、备份恢复、安全加固、版本升级和知识移交。
   2. 对集团单位，建议写月度运行分析或阶段性运维报告，内容包括系统使用情况、故障处理、风险提示和优化建议。
   3. 培训要分角色：管理人员、业务人员、系统管理员、运维人员，不同对象讲不同内容。

8. 验收、交付与服务承诺
   1. 验收口径必须来自采购文件，不能自创降低标准。
   2. 交付物要完整：软件系统、部署清单、账号权限清单、接口说明、测试记录、培训资料、运维手册、验收资料。
   3. 承诺要具体到时限、人员、机制和边界。

## 常用结构句式

这些句式用于统一正式风格，不要机械堆砌。

1. “本项目建设不以单点功能上线为目标，而以形成可运行、可检查、可追溯的业务闭环为交付标准。”
2. “方案在保持现有业务连续性的前提下，通过接口集成、数据归集和流程固化，减少重复填报和线下流转。”
3. “实施过程中以需求基线为控制依据，对新增需求和范围调整实行评估、确认、实施、验证和归档管理。”
4. “系统上线后通过运行台账、巡检记录和问题闭环机制，保证系统问题可定位、处理过程可追踪、服务结果可核验。”
5. “涉及 AI 分析的结果作为辅助判断依据，最终处置意见仍由具备职责权限的业务人员确认。”

禁用或慎用表达：

1. 不写“赋能、打造生态、保驾护航、全方位、至关重要、智慧大脑、引领未来”等空话。
2. 不写“完全杜绝风险、百分百准确识别、永久稳定运行”等无法兑现的承诺。
3. 不把政策背景写成大段宣传材料。正式方案要回到项目动作和交付责任。

## 图示建议

1. 治理对象关系图：检查任务、现场证据、AI 提示、整改事项、复查结论和审计记录之间的对象关系。
2. 证据链路图：视频流、关键帧、标注样本、模型输出、人工确认、整改材料和归档记录的证据链。
3. 质量门禁图：启动门禁、到货门禁、部署门禁、AI 验证门禁、联调门禁、验收门禁、质保门禁。
4. 交付作战图：20 天交付中各专业组并行推进和依赖关系，不画成普通线性流程。
5. 运维台账闭环图：服务受理、工单编号、处理、复测、确认、复盘、知识库沉淀。
6. 禁止直接复用 formal 模板常见的“系统总体架构图、业务闭环流程图、服务质量保障体系图”三件套；如果必须表达类似内容，也要换成对象关系、泳道、门禁或台账视角。

图示必须服务说明，不做装饰图。HTML/SVG 源码放 `生成文件/02-图示源码/`，截图放 `生成文件/03-图示截图/`，再插入 DOCX。

## 版式规则

1. 页面
   1. A4 纵向。
   2. 页边距建议：上 2.4 cm，下 2.2 cm，左右 2.5 cm。
   3. 页眉可使用项目名称或技术方案名称，页脚只保留页码。
   4. 与 formal 模板同时存在时，封面必须改用不同布局，例如左侧竖向标题线、项目要素卡片、目录式摘要或深色细栏，不能复用居中标题加基础信息表的封面。

2. 字体
   1. 中文正文：宋体，约 11 pt。
   2. 一级标题：黑体，约 14.5-15 pt，黑色或深灰色。
   3. 二级标题：黑体或加粗宋体，约 12.5 pt，黑色或深灰色。
   4. 三级标题：宋体加粗，约 11.5 pt，黑色或深灰色。
   5. 不使用蓝色标题文字。标题层级靠字号、字重、编号和留白体现。

3. 行距与段落
   1. 正文行距建议 1.35-1.45。
   2. 正文段后建议 6 pt。
   3. 段落比默认模板更短，适合正式材料审阅。

4. 表格
   1. 表格用于计划、职责、风险、交付物和服务响应，不把普通叙述强塞进表格。
   2. 表头可用浅灰底或白底加粗，表头文字使用黑灰色，保持稳重。
   3. 单元格必须设置内边距，跨页表格重复表头。
   4. 不使用蓝色字体表头、蓝色底表头或突兀彩色表头。

5. 色彩
   1. 主体黑灰色。
   2. 可使用深灰细线或极少量深红棕、墨绿灰作为弱强调，但不要大面积色块。
   3. 不使用蓝色标题、蓝色表头、营销式封面、渐变、彩色卡片和夸张装饰。

## 交付前检查

1. 是否站在业主单位和集团管理视角，而不是供应商自夸视角。
2. 是否写清业务责任链、数据责任链和服务责任链。
3. 是否把质量、进度和变更控制写成可执行机制。
4. 是否避免空泛政策口号和互联网营销词。
5. 是否保留采购文件要求的技术、服务、交付、验收和售后承诺。
6. 是否对第三方接口、现场条件、数据质量、信创适配、AI 误报漏报等风险给出边界和应对。
7. 是否存在连续堆表格、普通说明表格化、表格前后缺少解释的问题。
8. 标题和表头是否保持黑灰正式，是否误用了蓝色字体、蓝色表头或突兀彩色底色。
9. 正文是否没有写作过程、思考过程、用户提示词、模板选择说明和“如何遵守要求”的解释。
10. 正文是否没有“待确认、需明确、暂按、后续确认”等未定稿表达。
11. 图示是否已由 SVG/HTML 截图插入 DOCX，源码和截图是否按目录保存。
12. 最终 DOCX 是否位于 `生成文件/01-交付文档/`。
