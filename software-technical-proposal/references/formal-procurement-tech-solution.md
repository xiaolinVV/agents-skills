# formal-procurement-tech-solution

## 适用场景

1. 软件行业采购、竞争性磋商、招标响应、政企平台建设、AI+行业应用、系统集成项目。
2. 用户希望输出正式、专业、可直接交付的技术方案 DOCX。
3. 采购文件中包含“系统总体设计方案、服务质量保障、质量控制、人力物力投入、售后服务”等技术评分项；如采购文件明确要求系统布局、创新性、先进性或可扩展性，再启用对应章节。
4. 采购文件同时要求技术方案和偏离表、承诺表、支撑材料索引时，启用 `appendix_mode`，在叙述正文后追加法定附表。

## 模板定位

1. 文档外观：正式、克制、商务化，重视阅读舒适度，不做花哨彩色模板。
2. 正文风格：像项目技术负责人写的方案，语言具体，少口号，少套话。
3. 结构策略：覆盖评分关注点，但不暴露评分导向。
4. 交付形态：DOCX 为主，图示 HTML/SVG 和截图为支撑产物。
5. 版式基调：默认黑灰正式。标题、正文和表头文字使用黑灰色；不用蓝色字体、蓝色表头或彩色卡片制造层级。

## 推荐目录

按项目内容裁剪，不要机械保留所有章节。以下目录是候选骨架，不是固定目录；生成前必须按采购文件和项目事实逐项判断保留、合并、改名、删除或新增。专项技术章节必须按项目能力命名，不能把其他项目的专有标题带入新项目。

1. 项目业务情况理解
   1. 建设目标
   2. 建设范围
   3. 使用对象与职责边界
   4. 业务闭环

2. 需求分析与整体要求响应
   1. 功能需求拆解
   2. 非功能需求
   3. 质量属性设计
   4. 交付和服务要求

3. 系统总体设计方案
   1. 设计原则
   2. 应用架构
   3. 数据架构
   4. 专项技术链路（按项目内容命名，如智能识别链路、视频分析链路、数据治理链路、集成接口链路；无对应内容则删除）
   5. 接口设计
   6. 安全设计
   7. 部署与运行设计

4. 部署与界面组织（可选）
   1. 物理部署布局
   2. 逻辑布局
   3. 界面布局
   4. 权限布局

5. 方案特点与适配性说明（按评分要求启用）

   2. 技术先进性或创新性
   3. 可扩展设计

6. 服务质量保障措施
   1. 服务质量目标
   2. 质量控制措施
   3. 人力投入安排
   4. 物力投入安排
   5. 实施进度安排
   6. 风险控制
   7. 服务事件管理
   8. 文档与知识移交

7. 培训、验收与售后服务
   1. 培训安排
   2. 验收配合
   3. 售后服务

8. 结论与承诺

   1. 采购需求偏离表
   2. 合同条款偏离表
   3. 支撑材料索引
   4. 培训计划表
   5. 验收项表

## 内容写法

0. 目录裁剪
   1. 先从采购文件抽取必写章节、评分关注点和交付边界，再形成最终目录。
   2. 模板章节没有项目依据时删除或合并；采购文件明确要求但模板没有时新增。
   3. 标题必须贴合项目内容。不得无脑保留“AI 分析链路”等当前项目专有标题；只有采购文件确实涉及 AI、模型、视频智能识别等内容时，才设置对应专项技术章节，并按具体能力命名。

### 表格使用边界

1. 本模板是叙述型正式技术方案，不是逐条响应矩阵。普通项目理解、建设思路、技术路线、服务机制优先写成短段落和编号列表。
2. 只有条款对照、接口清单、角色分工、进度安排、风险控制、交付物和验收口径等结构化内容才使用表格。
3. 表格前后要有说明文字，解释该表解决什么问题、如何落到实施动作。不要连续堆表格。

### 交付正文边界

1. 正文只呈现可交付的技术方案，不写写作过程、思考过程、目录取舍理由、模板选择理由或 agent 对话痕迹。
2. 用户对语气、表格、措辞、风格提出的注意事项，只作为内部约束吸收。正文直接呈现调整后的结果，不解释“为避免某种语气”“按照某项要求”。
3. 不确定的关键事实不得写入 DOCX。涉及范围、参数、工期、验收、承诺或责任边界不清楚时，先向用户确认；确认前不写“待确认、需明确、暂按、后续确认”等未定稿表达。
4. 正文不得出现“本文将、以下从几个方面、根据用户要求、按照您的要求、模板建议、AI 生成、评分响应、评委”等过程性或答题卡式表述。
5. 采购文件指定的响应函、偏离表、合同条款偏离表、承诺表等固定格式表单，允许保留采购文件用语；这些用语不得扩散到叙述性正文。
6. 数字型承诺必须来自采购文件或用户确认事实。工期、质保期、到场时间、SLA、人员数量、接口数量和设备数量不清楚时，不写入 DOCX。
7. 关键承诺必须可定位到章节号、图号、附表号、附件号或页码锚点，不写“详见正文”。

1. 项目业务情况理解
   1. 先写项目真实业务问题，不要直接堆功能。
   2. 用“现状问题、系统要解决什么、业务闭环如何形成”组织开头。
   3. 对消防、政务、监管、医疗、教育等行业项目，要写清业务职责边界。

2. 需求分析与整体要求响应
   1. 把采购文件中的技术参数转成方案语言。
   2. 对关键要求可以使用“要求关注点/方案安排/交付口径”小表，但不要把整章写成表格，也不要把表头写成“评分响应”。
   3. 星号条款、交付时间、质保响应、验收资料必须进入正文。

3. 系统总体设计方案
   1. 先给设计原则，再给架构图。
   2. 应用架构要能落到模块职责。
   3. 数据架构要说明核心数据域及追溯关系。
   4. AI 项目必须写清数据标注、训练/推理、模型版本、误报回流和人工确认。
   5. 接口设计要强调“不破坏现有系统”，用接口层和映射关系处理存量平台。

4. 部署与界面组织
   1. 只有采购文件要求系统布局、部署布局、界面组织、权限体系或硬件部署时才单列；否则并入系统总体设计方案。
   2. 写物理部署、逻辑服务、界面入口和权限边界。
   3. 硬件类采购要写服务器、数据库、AI 服务器、交换机等部署对象。
   4. 不要只写“采用云平台/微服务”，必须说明每个对象承担什么。

5. 方案特点与适配性说明
   1. 只有评分办法明确要求创新性、先进性、适用性、可扩展性时才单列；普通项目并入系统总体设计或需求响应章节。
   2. 创新点要来自项目场景，不要写空泛技术名词。
   3. 每个特点后面说明为什么适用于本项目、落到哪个业务动作或交付物。
   4. AI、LLM、视觉模型等能力要和业务流程相连。

6. 服务质量保障措施
   1. 这部分属于技术方案正文，不另起独立文件。
   2. 质量控制要覆盖需求基线、设计复核、硬件到货、软件部署、数据标注、模型验证、联调测试、验收控制。
   3. 人力投入要写岗位和职责，不只写人数。
   4. 物力投入要写硬件设备、部署工具、AI 工具、实施辅材、备机备件、资料材料。
   5. 进度安排要按采购文件工期拆成阶段，写清每阶段工作、质量控制点和交付物；没有明确工期时，不编造天数。
   6. 风险控制要写真实风险：现场环境、原始数据质量、AI 误报漏报、接口适配、硬件故障、资料缺失。
   7. 售后服务要照采购文件承诺响应时间、到场时间、备用货物、质保年限；采购文件未明确且用户未确认时，不虚写数字承诺。

### 附录模式

1. 采购文件要求固定附表时，在正文后追加附录，不把整篇叙述型方案改成矩阵响应书。
2. 附录常用表包括采购需求偏离表、合同条款偏离表、支撑材料索引、培训计划表、验收项表。
3. 附录表格按采购文件格式优先。采购文件没有格式时，使用“条款号/要求摘要/响应内容/偏离情况/支撑材料位置”的稳定列结构。
4. 附录中的支撑材料位置必须写章节号、图号、附表号、附件号或页码锚点。

## 图示建议

1. 系统总体架构图：现场采集层、通信与接入层、业务平台与数据层、AI 分析层、数据库/硬件层。
2. 业务闭环流程图：任务派发、现场记录、实时回传、抽帧分析、风险描述、人工确认、整改派发、整改反馈、复查确认、归档统计。
3. 服务质量保障体系图：质量控制、人力投入、物力投入、进度管理、维保响应、资料移交。
4. 接口关系图：现有平台、移动终端、AI 分析服务、整改反馈端、业务数据库。

图示必须用 SVG 代码保存为 HTML，再截图插入 DOCX。HTML 文件应可在浏览器直接预览。

## 输出物目录约定

默认在项目工作目录下创建 `生成文件/formal-procurement-tech-solution/`。如用户已有明确目录，以用户要求为准；同一采购文件使用多个模板时，不得混放产物。

1. `生成文件/formal-procurement-tech-solution/01-交付文档/`
   1. 保存最终 DOCX。
   2. 如需要 PDF 版正式交付，也保存在这里。
   3. 文件名格式优先使用“项目名称-技术方案.docx”。

2. `生成文件/formal-procurement-tech-solution/02-图示源码/`
   1. 保存图示 HTML/SVG 源码。
   2. 文件名使用两位序号加图名，例如 `01-系统总体架构图.html`。
   3. 源码必须能在浏览器中直接预览。

3. `生成文件/formal-procurement-tech-solution/03-图示截图/`
   1. 保存由图示源码截图得到的 PNG。
   2. 文件名与图示源码保持同序号、同标题，例如 `01-系统总体架构图.png`。
   3. DOCX 插图优先引用该目录下的 PNG。

4. `生成文件/formal-procurement-tech-solution/04-过程文件/`
   1. 保存生成脚本、需求抽取记录、结构化中间稿等可维护材料。
   2. 如果项目只是一次性交付，可只保留生成脚本和必要记录。
   3. 不把该目录内容作为正式交付物展示给用户，除非用户要求。

5. `生成文件/formal-procurement-tech-solution/90-质检预览/`
   1. 保存 DOCX 渲染页、临时 PDF、contact sheet 等视觉检查文件。
   2. 该目录用于内部质检，最终答复前默认清理。
   3. 用户要求查看预览时可以保留并说明用途。

6. `生成文件/formal-procurement-tech-solution/99-临时文件/`
   1. 保存转换碎片、临时下载、失败截图等任务过程临时文件。
   2. 任务结束前清理。

交付答复中优先只链接 `01-交付文档/` 下的最终文件。不要把质检目录、临时目录当成交付结果。

## 版式规则

1. 页面
   1. A4 纵向。
   2. 页边距建议：上 2.3-2.5 cm，下 2.1-2.3 cm，左右 2.4-2.6 cm。
   3. 页脚只保留页码即可，页眉可为空或使用低调项目名。

2. 字体
   1. 中文正文：宋体，约 11 pt。
   2. 一级标题：黑体，约 14-15 pt，加粗，黑色或深灰色。
   3. 二级标题：黑体或加粗宋体，约 12-12.5 pt，黑色或深灰色。
   4. 三级标题：约 11-11.5 pt，黑色或深灰色。
   5. 不使用蓝色标题文字。标题层级靠字号、字重、编号和段前段后间距体现。

3. 行距与段落
   1. 正文行距建议 1.32-1.40，推荐 1.36。
   2. 正文段后建议 6-8 pt，推荐 7 pt。
   3. 列表行距建议 1.25-1.32，推荐 1.30。
   4. 表格内行距建议 1.10-1.18，避免页数失控。

4. 列表
   1. 序号类内容优先用真实 Word 编号列表。
   2. 每组编号应从 1 重新开始。
   3. 不使用黑点、圆点、短横线作为主要结构。

5. 表格
   1. 表格使用白底、细边框、表头加粗。
   2. 表头使用黑灰文字，底色为白色或极浅灰色。
   3. 单元格必须设置内边距，避免文字贴边。
   4. 表格宽度和列宽按内容分配，长文本列更宽。
   5. 表格与上下正文之间保留间距。
   6. 不使用蓝色表头、蓝色字体表头或突兀表头底色。

6. 色彩
   1. 主体黑灰色。
   2. 弱强调优先使用细灰线、浅灰底、字重和留白。
   3. 除采购文件或用户模板明确要求外，不使用蓝色标题、蓝色表头、蓝色标题线、大面积蓝色标题块、彩色卡片和营销式封面。

## 交付前检查

1. 文件名是否按用户要求命名。
2. 最终 DOCX 是否位于 `生成文件/formal-procurement-tech-solution/01-交付文档/`。
3. 封面是否只保留正式标题和必要项目信息。
4. 叙述性正文是否没有“评分响应、评委、模板来源、AI 生成”等不该出现的词；采购文件指定的法定表单用语是否只出现在对应表单中。
5. 服务质量保障是否在技术方案正文中。
6. 图示是否已由 SVG/HTML 截图插入 DOCX，源码和截图是否按目录保存。
7. 编号列表是否真实、顺序正确、每组重启。
8. 是否存在连续堆表格、普通说明表格化、表格前后缺少解释的问题。
9. 标题和表头是否保持黑灰正式，是否误用了蓝色字体、蓝色表头或突兀彩色底色。
10. 正文是否没有写作过程、思考过程、用户提示词、模板选择说明和“如何遵守要求”的解释。
11. 正文是否没有“待确认、需明确、暂按、后续确认”等未定稿表达。
12. 数字型承诺是否有来源，关键承诺和支撑材料是否有章节号、图号、附表号、附件号或页码锚点。
13. 启用 `appendix_mode` 时，正文、采购需求偏离表、合同条款偏离表和支撑材料索引是否一致。
14. 渲染页面是否无重叠、无截断、无异常空白、无表格贴边。
15. `90-质检预览/` 和 `99-临时文件/` 是否按用户要求保留或清理。
