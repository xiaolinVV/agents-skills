# 软件行业技术方案生成

## 工作原则

1. 先读采购文件、评分办法、技术规格和商务服务要求，再写方案。不要只按标题发挥。
2. 正式交付文档不得暴露写作过程。正文不要出现“评分响应”“评委”“模板来源”“AI 生成”“编制依据”等过程性表述；“投标”字样按采购文件和用户要求控制。
3. 技术方案可以覆盖评分关注点，但正文表达应像正式交付文件，而不是给评审看的答题卡。
4. 服务质量保障、售后响应、质保、人员投入、物力投入、进度控制等内容是技术方案的一部分，不要默认拆成独立文件。
5. 常规技术方案应尽量多配图。系统总体设计、应用架构、数据架构、部署运行、业务闭环、AI 链路、接口集成和服务保障等章节，优先用专业架构图或流程图承载关系，不要只堆文字和表格。
6. 模板目录是可裁剪骨架，不是固定目录。章节必须按采购文件、项目内容和用户要求裁剪、合并、改名或新增；不得机械保留模板所有章节，也不得脱离项目事实随意增加章节。这是铁律。
7. 章节标题必须通用且贴合项目事实。不要把某个项目的专有技术点固化成通用标题，例如没有 AI 要求的项目不应保留“AI 分析链路”；有 AI 要求时也应按项目真实能力命名为“智能识别链路”“视频分析链路”“模型推理链路”等更准确标题。
8. 避免 AI 腔。少用“赋能、打造、生态、全方位、至关重要、综上、保驾护航、深度融合”等空泛词。用具体业务动作、交付物、责任边界、验收口径替代口号。
9. 如需生成 DOCX，优先联动 `documents` skill 或等价 DOCX 工具，必须渲染为页面图片进行视觉检查后再交付。
10. 模板差异化是铁律。同一采购文件使用不同模板生成技术方案时，必须体现不同供应商的编写风格；结构、内容组织、行文语气、表格形态、图示主题、图示视觉风格、封面和版式都要明显不同。不得把上一模板的目录、段落、图名、SVG 布局、表格清单和常用句式换皮复用。
11. 采购事实可以相同，表达方案必须不同。项目名称、采购人、交付期、质保期、技术参数等事实来自采购文件，允许一致；围绕这些事实形成的论证路径、章节顺序、图示模型、服务组织叙述和版式呈现必须重新设计。
12. 如果模板之间无法生成明显不同的供应商风格，说明模板失效，必须先整改模板规则，再重写文档。不能用“模板名称不同”冒充“供应商风格不同”。
13. 默认版式采用黑灰正式风格。标题、正文和表格文字默认使用黑灰色；不得把蓝色字体、蓝色表头、蓝色标题线作为默认风格。需要弱强调时，优先使用字号、字重、编号、段前段后间距、细灰线或浅灰底。
14. 叙述型技术方案以正文、图示和必要表格共同表达。`formal-procurement-tech-solution` 和 `fujian-soe-steady-narrative-tech-solution` 不要把普通说明、章节概述、建设思路、服务机制强塞进表格；`compliance-matrix-procurement-response` 才是表格密集型响应书。
15. 交付正文只写可交付内容。正文不得出现写作过程、思考过程、取舍理由、模板使用说明、提示词响应、与用户对话痕迹或 agent 自我说明。
16. 用户提出的“不要某种语气、注意某点、必须怎么样”等内容，只能作为内部写作约束吸收，不得显式写入方案正文。最终文档要直接呈现符合约束后的正式方案，而不是解释如何遵守约束。
17. 关键事实不确定时，先向用户确认再写入正式方案。不得在交付 DOCX 正文中写“待确认、需确认、暂按、后续明确、建议进一步确认”等未定稿表达；确需表达边界时，必须改写为正式的前置条件、配合事项、风险控制或实施边界。

## 交付正文边界

1. 正文允许写：
   1. 项目事实、建设目标、需求分析、技术架构、功能设计、数据链路、接口关系、部署安排、安全措施。
   2. 实施计划、质量控制、风险控制、培训验收、售后服务、交付物、响应承诺和责任边界。
   3. 来源于采购文件或用户已确认事实的前置条件、配合事项和风险边界。
2. 正文禁止写：
   1. “根据用户要求、按照您的要求、为避免某种语气、本文将、以下从几个方面、我们在撰写时、生成过程中、模板建议、AI 生成、提示词”等面向写作过程或 agent 过程的表述。
   2. “本节响应评分点、为了获得高分、评分关注点、评委可见”等答题卡式表述。
   3. “待确认、需进一步明确、暂按、如后续确认、建议业主确认”等未定稿表述。采购文件要求列出风险事项时，也要改写为正式的风险边界、前置条件或配合事项。
3. 用户提示处理规则：
   1. 用户说“不要营销语气”，正文直接写成克制、具体、正式的方案，不写“本方案避免营销语气”。
   2. 用户说“不要大量表格”，正文直接减少表格，不写“为避免表格过多”。
   3. 用户说“正式一点、真实可交付”，正文直接按正式交付方案写，不写“按照正式风格编写”。
4. 不确定事项处理规则：
   1. 影响范围、参数、工期、验收、偏离、承诺、费用、责任边界的关键事实不清楚时，暂停对应正文生成并先问用户。
   2. 不影响承诺的措辞、章节顺序、表述详略，由 agent 直接按正式方案风格处理，不向正文暴露内部判断。
   3. 用户确认后再写入 DOCX；未确认的信息只可放在交付聊天说明中，不写进正式文档。

## 模板选择

1. 用户明确指定模板时，按用户选择执行。
2. 用户未指定模板，但任务是软件采购、政企项目、竞争性磋商、技术评分项响应，默认使用 `formal-procurement-tech-solution`。
3. 用户要求“更商务”“更高级”“正式交付”“不要像答题”时，也默认使用 `formal-procurement-tech-solution`。
4. 用户要求“福建国企风格”“省属国企风格”“集团型企业正式方案”“稳健正式”“国企内部材料感”“信创/数据治理/集团管控/长期运营导向”时，使用 `fujian-soe-steady-narrative-tech-solution`。
5. 用户要求“政府采购响应文件风格”“逐条响应”“表格式”“技术偏离表”“采购需求响应表”“矩阵式响应”“技术部分响应书”时，使用 `compliance-matrix-procurement-response`。
6. 用户要求“双盲”“暗标”“匿名技术标”时，优先使用 `compliance-matrix-procurement-response`，并按采购文件删除供应商可识别信息。
7. 新增模板时，在 `references/` 下新增一个模板文件，并在本节补充选择规则。

当前可用模板：

1. `formal-procurement-tech-solution`：正式采购类软件技术方案模板。适合政企软件、平台建设、AI/数据/系统集成类项目。读取 `references/formal-procurement-tech-solution.md`。
2. `compliance-matrix-procurement-response`：政府采购技术响应书/矩阵式合规模板。适合逐条响应采购需求、技术响应偏离表、服务承诺、证明材料索引、暗标或双盲技术标。读取 `references/compliance-matrix-procurement-response.md`。
3. `fujian-soe-steady-narrative-tech-solution`：福建国企稳健叙述型技术方案模板。适合省属国企、集团型企业、信创、数据治理、集团管控、长期运营和正式内部材料风格。读取 `references/fujian-soe-steady-narrative-tech-solution.md`。

## 标准流程

1. 资料读取
   1. 提取项目名称、项目编号、采购人、采购标的、交付周期、质保期、响应时间、验收要求。
   2. 提取技术规格中的模块、算法、接口、部署、数据、硬件、适配、培训和服务要求。
   3. 提取评分办法中的技术项重点，但不要把“评分”语言搬进正文。
   4. 标记实质性要求、星号条款、时间承诺和不可负偏离事项。
   5. 标记会影响承诺或偏离判断的不确定事项。关键事实不清楚时先问用户，不把未确认信息写入正式 DOCX。

2. 内容建模
   1. 把采购要求转成“业务链、系统能力、部署对象、数据链路、AI 链路、服务链路”。
   2. 对软件项目优先写清数据结构和流程闭环：任务从哪里来，数据在哪里形成，谁确认，怎么整改，如何归档。
   3. 对 AI 项目必须写清人工确认边界。AI 是辅助，不替代业务人员或执法人员的最终判断。
   4. 对服务质量保障必须写成可执行措施，包括人员、物力、进度、质量控制、风险控制、事件管理和资料移交。
   5. 建模时同步建立“配图清单”。凡是出现层级、流向、拓扑、闭环、接口、数据域、部署对象、责任分工、进度门禁的内容，优先判断是否需要图示，而不是等正文写完再补装饰图。

3. 正文组织
   1. 先根据采购文件和用户要求确定最终目录，再参考模板骨架。模板章节只能作为候选项，必须逐项判断“保留、合并、改名、删除、新增”。
   2. 每章只写正式方案内容，不写“本节响应某评分点”。
   3. 先判断内容类型，再决定是否用表格。能用 2-5 个短段落讲清的方案说明写成正文；需要逐项比较、条款对照、责任分工、时间节点、交付物、风险等级、接口字段、偏离情况时才用表格。
   4. 表格用于对照、分工、计划、风险、接口、部署等结构化信息；普通说明不要强塞进表格。连续出现多张表时，必须穿插必要解释，说明表格之间的关系和落地动作。
   5. 序号类内容优先使用有序编号。除非用户明确要求，不使用黑点无序列表。
   6. 不得机械保留模板章节。采购文件没有对应内容、项目不涉及该能力、或该章节会造成牵强表达时，删除或合并；采购文件有明确要求但模板没有时，必须新增相应章节。
   7. 不得随意新增章节。新增章节必须能对应采购要求、项目实际能力、交付边界、验收口径或必要风险控制；不能为了显得丰富而增加空章节。
   8. 专项技术章节要按项目命名。AI、物联网、GIS、视频、数据治理、信创、集成接口等只在项目真实涉及时出现，标题使用项目内的具体能力名，不套用其他项目标题。
   9. 如果同一项目目录下已经存在其他模板产物，必须先读取其目录、图名、图示截图、主要段落开头和表格标题，建立差异化避让清单。新文档不得沿用相同一级目录序列，不得沿用相同图示标题组合，不得沿用相同开篇论证路径。
   10. 不同模板产物应像不同供应商独立编制：可以覆盖同一评分点，但应使用不同的叙事框架。例如一个供应商按“业务闭环+技术能力”组织，另一个供应商应按“治理对象+运行机制+交付管控”组织，而不是改几个小标题。
   11. 用户给 agent 的注意事项必须内化为写作约束，不得原样或换皮写入正文。正文要呈现结果，不解释写作策略。

4. 图示制作
   1. 常规正式技术方案默认应配置多张图。除非采购文件极短或用户明确要求精简，否则不要只放 1-2 张泛泛的总体图。
   2. 系统总体设计章节的高优先级架构图包括：系统总体架构图、应用架构图、数据架构图、部署与运行架构图。若正文设有这些小节，应在对应小节附近插入对应图，不能用同一张“总体架构图”代替所有架构。
   3. 其他常见图示场景包括：业务闭环流程图、专项技术链路图（如智能识别、视频分析、数据治理、物联感知、模型推理等，按项目内容命名）、接口集成关系图、网络/物理拓扑图、安全架构图、权限模型图、服务质量保障体系图、实施进度与质量门禁图。按项目真实内容选择，不为凑数量硬画。
   4. 技术架构图、业务架构图、流程图、服务保障体系图应先用 SVG 代码绘制并保存为可预览 HTML。
   5. 用浏览器截图生成 PNG 后插入 DOCX。图示文件命名、图号、caption 和 `manifest.json` 必须一致；同一模板再次生成时应清理旧图，避免目录里残留过期图示。
   6. 图示应服务理解，不要做装饰图。图中节点使用业务名词和技术名词，不堆营销词；文字必须可读，不能越界、重叠或贴边。
   7. 架构图要表达关系：分层、依赖、数据流、控制边界、运行职责或闭环反馈至少要说明其中一种。只有模块盒子没有流向和边界的图，价值很低，应重画。
   8. 不同模板不得复用同一套图示源码、节点布局或图名。至少应更换图示视角、图形构图和视觉语言：例如从“系统分层架构图”改为“监管对象—数据证据—处置闭环关系图”，从横向流程改为泳道图、矩阵图、环形闭环图或分区治理图。
   9. 图示差异化不等于换颜色。节点命名、关系表达、图形结构和说明重点都要不同。

5. 输出物保存
   1. 在项目工作目录下统一创建 `生成文件/<template_id>/`，不要把不同模板的输出物混放在同一个主目录。`template_id` 必须使用当前模板的稳定英文 ID，例如 `formal-procurement-tech-solution`。
   2. 同一采购文件使用不同模板生成时，每个模板独占一个主目录：`生成文件/formal-procurement-tech-solution/`、`生成文件/compliance-matrix-procurement-response/` 等。
   3. 默认允许同一模板的再次生成覆盖该模板目录内的旧产物；如果用户要求保留多轮版本，再增加 `生成文件/<template_id>/<run_id>/` 或 `生成文件/<template_id>/v1/` 这一级。不要默认制造时间戳目录。
   4. 最终交付文档放入 `生成文件/<template_id>/01-交付文档/`，文件名使用“项目名称-技术方案.docx”或用户指定名称。
   5. 图示 HTML/SVG 源码放入 `生成文件/<template_id>/02-图示源码/`，命名使用“01-系统总体架构图.html”这类带序号的名称。
   6. 图示截图放入 `生成文件/<template_id>/03-图示截图/`，文件名与图示源码保持同序号、同标题。
   7. 生成脚本、结构化中间稿、抽取记录等可维护文件放入 `生成文件/<template_id>/04-过程文件/`。只有在后续维护需要时才保留。
   8. 在 `生成文件/<template_id>/manifest.json` 记录源采购文件、项目名称、模板 ID、模板名称、生成时间和主要输出文件，方便之后区分不同模板产物。
   9. DOCX 渲染页、临时 PDF、contact sheet 等质检文件放入 `生成文件/<template_id>/90-质检预览/`，交付前默认清理；用户要求查看时才保留。
   10. 临时下载、转换碎片和失败产物放入 `生成文件/<template_id>/99-临时文件/`，任务结束前清理。

6. DOCX 排版
   1. 使用 A4 纵向页面，中文正式文档字体体系，标题层级清晰。
   2. 正文不要密排。正式技术方案常用 1.3-1.5 倍行距，段后留白；表格可略紧凑但必须有内边距。
   3. 页眉页脚保持克制，避免花哨装饰。页码清晰即可。
   4. 标题文字默认黑色或深灰色，不使用蓝色字体。标题层级靠字号、字重、编号、段前段后间距和细分隔线建立。
   5. 表格表头优先用白底或极浅灰底、细边框、黑灰文字、适度加粗；不使用蓝色字体、蓝色表头或突兀色块。
   6. 色彩只作弱辅助。除采购文件、用户模板或品牌规范明确要求外，不使用蓝色标题块、蓝色表头、彩色卡片、大面积渐变或营销式封面。

7. 质检
   1. 检查采购文件关键要求是否覆盖。
   2. 检查正文是否出现用户要求避免的词。
   3. 检查列表是否为真实编号列表，且每组编号重新开始。
   4. 检查目录是否按项目裁剪：无关章节是否删除，缺失章节是否补齐，专项技术标题是否贴合本项目，是否残留其他项目味道的标题。
   5. 检查表格使用是否克制：叙述型方案不得连续多页只有表格；普通说明不得被拆成无意义表格；响应矩阵型模板除外。
   6. 检查版式是否黑灰正式：标题、正文和表头不得默认使用蓝色字体；表头不得使用蓝色底色或突兀彩色底色。
   7. 检查正文是否暴露写作过程、思考过程、模板来源、用户提示词、agent 对话痕迹或“如何遵守要求”的解释。
   8. 检查正文是否出现未定稿表达：待确认、需确认、需进一步明确、暂按、后续确认、建议进一步确认。发现后先向用户确认，不能直接交付。
   9. 渲染 DOCX，逐页检查重叠、截断、表格贴边、异常空白、图示模糊、页眉页脚怪异。
   10. 如果同一采购文件已有其他模板产物，增加差异化质检：一级目录重合度、图示标题重合度、连续段落相似度、表格标题复用情况、封面和页面视觉相似度。发现明显相似时，必须重写，不得交付。
   11. 只向用户交付最终 DOCX；渲染图片和临时 PDF 除非用户要求，否则作为内部检查产物处理。

## 经验说明

这类软件行业技术方案没有单一强制的“行业官方模板”。本 skill 中的默认模板来自三类经验的合并：

1. 政企采购/竞争性磋商技术方案的常见章节结构。
2. 正式中文商务 Word 文档的排版习惯。
3. 文档生成工作流中的正式商务简报/叙述型方案设计原则。

因此，不要声称模板来自某个官方行业标准，除非用户提供了明确模板、规范或单位标准文件。

公开采购文件中常见的“技术方案”和“技术响应偏离表”通常是不同部分：技术方案可以格式自定、以叙述和图示说明为主；偏离表、逐条响应表才天然适合表格化。默认生成正式技术方案时，不要把矩阵响应书的表格密度套到叙述型方案上。

新增的 `compliance-matrix-procurement-response` 来自政府采购公开招标和竞争性磋商文件中常见的响应文件格式经验：技术方案、技术响应偏离表、商务响应偏离表、服务承诺、逐条响应和支撑材料索引。它不是全国统一官方模板；使用时仍以具体采购文件给出的格式为准。

新增的 `fujian-soe-steady-narrative-tech-solution` 来自福建信息化工程招标文件示范文本中对项目理解、技术服务、系统集成、实施调试、培训、运行维护、进度控制和变更控制的常见要求，以及福建省属国资国企数字化转型、信创适配、数据治理、合规管理和集团管控类公开材料的写作风格经验。它不是官方模板；使用时仍以具体采购文件和业主单位要求为准。
