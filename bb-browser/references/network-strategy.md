# 联网任务决策策略

这份策略用于复杂信息获取、登录态页面、反爬页面、事实核实和多来源调研。它只规定路径选择，不改变 `bb-browser` 的命令语义。

## 快速决策树

```text
1. 明确目标内容和完成标准
2. 判断数据最可能在哪里
3. 有 site adapter 就优先用 adapter
4. 能用 fetch 获取接口或页面数据，就先 fetch
5. 需要页面结构或 JS 渲染时，open 页面并读取 DOM
6. 需要用户动作时，再 snapshot -i 后点击、填写、滚动
7. 核实任务必须回到一手来源
8. 每一步用结果校验方向，失败就换路径
9. 完成后关闭自己打开的 tab
```

## 路径选择

| 场景 | 优先方式 | 原因 |
|------|----------|------|
| 平台已有 adapter | `bb-browser site <name>` | adapter 已封装站点逻辑、登录判断和 tab 管理 |
| 已知 API 或页面请求 | `bb-browser fetch <url>` | 在浏览器上下文中携带 Cookie 和登录态 |
| 已知页面，需要正文、链接或结构 | `bb-browser open` + `bb-browser eval` | DOM 里常有完整正文、隐藏内容和真实链接 |
| 需要点击、填写、翻页、上传 | `bb-browser snapshot -i` + `click/fill/scroll/upload` | 先拿可交互元素，再执行用户动作 |
| 需要页面视觉状态 | `bb-browser screenshot` | 用于验证渲染、图像内容或视频当前帧 |
| 需要调试接口 | `bb-browser network requests` | 直接观察页面真实请求和响应 |

不要把浏览器当第一反应。能用 adapter 或 fetch 稳定拿到数据，就不要先点页面。浏览器操作成本更高，也更容易受布局变化影响。

## 一手来源原则

搜索、热榜和聚合页面只用于发现来源，不能直接证明事实。核实任务必须尽量回到原始发布方：

| 信息类型 | 一手来源 |
|----------|----------|
| 政策法规 | 发布机构官网 |
| 企业公告 | 公司官网、投资者关系、官方新闻页 |
| 学术信息 | 原始论文、机构官网 |
| 工具能力和用法 | 官方文档、源码 |
| 产品价格或规则 | 官方定价页、服务条款、控制台说明 |

如果找不到官方原文，才使用权威媒体原创报道，并说明这是次级来源，存在转述误差可能。多个转载源重复同一说法，不等于事实。

## 过程校验

每一步结果都要回答：

- 内容是否接近目标？
- 失败是权限、登录态、反爬、JS 渲染、URL 参数缺失，还是目标不存在？
- 是否应该换路径，而不是机械重试同一个命令？

页面提示“内容不存在”不一定可信。它可能是 URL 参数缺失、访问方式异常、未登录、触发风控或静态请求失效造成的。

## 静态优先，浏览器兜底

推荐顺序：

```text
site adapter
-> fetch
-> open + eval 读取 DOM
-> snapshot -i + 页面交互
-> network / console / errors 调试
```

对登录后后台、复杂 SPA、微信公众号、小红书、内部系统等静态层经常失效的站点，可以更早进入真实浏览器。

## 先读结构，再操作页面

进入页面后不要先乱点。先查看：

- 当前 URL 和 title
- `snapshot -i` 中的按钮、链接、输入框
- `eval` 读取的正文、链接、表单、媒体资源
- 是否已有隐藏内容、折叠内容、轮播内容或懒加载内容在 DOM 中

很多内容已经在 DOM 里，只是没有显示。能直接 `eval` 提取，就不要用多次点击模拟人眼浏览。

## 保留站点生成的完整 URL

站内链接经常携带必要参数，例如 token、上下文参数、分页参数或跳转参数。从 DOM 里拿到的 `href` 尽量完整保留，不要随意裁剪。

手工拼接 URL 失败时，优先怀疑缺少站点上下文参数。

## fetch 与 GUI 的取舍

`bb-browser fetch` 适合稳定接口和已知资源；GUI 操作适合必须由页面状态驱动的流程。

| 方式 | 适合 | 风险 |
|------|------|------|
| `fetch` / `eval` | 快速读取接口、正文、链接、结构化数据 | 手工构造请求可能缺上下文 |
| `snapshot -i` + 交互 | 登录、表单、翻页、展开、上传 | 慢，依赖页面结构 |
| `network requests` | 逆向页面真实请求 | 输出可能很大，需要过滤 |

当程序化路径受阻，退回页面交互；当页面交互太慢或不稳定，观察 network 后改用 fetch。

## 媒体内容

如果核心内容在图片或视频里，优先从 DOM 提取资源 URL：

```bash
bb-browser eval "[...document.images].map(img => img.src).filter(Boolean).join('\n')"
bb-browser eval "[...document.querySelectorAll('video, source')].map(v => v.src).filter(Boolean).join('\n')"
```

公开资源可直接访问或下载；需要登录态的资源用浏览器上下文处理。整页截图是兜底，不是首选。

## 登录判断

不要一看到登录按钮就停。只判断一件事：目标内容是否已经拿到。

只有确认目标内容因为未登录无法获取，并且登录能解决时，才提示用户登录。用户登录后刷新页面继续，不要重启整个任务。

## 并行调研边界

适合并行：

- 多个互不依赖的网站
- 多个产品官网对比
- 多个来源交叉核实
- 多页资料分别读取

不适合并行：

- 下一步依赖上一步结果
- 单页简单查询
- 几次 fetch 或 eval 就能完成的小任务

并行的目标是减少等待和隔离上下文，不是让简单任务变复杂。
